# Decision log

Design choices that shaped ShuttleSense, in number order. D24–D27 were written down on Nov 14 with the dates the decisions were made, so their dates are earlier than D23's. Add a row in the PR that makes the decision; if a later decision replaces an earlier one, add a new row and mark the old one *superseded*.

| # | Date | Decision | Alternatives considered | Reason | Owner |
| --- | --- | --- | --- | --- | --- |
| D1 | 2026-10-29 | One Flutter client (Android, iOS, Web, Windows) talking REST to a Python FastAPI backend | Streamlit/Gradio web UI; native Android app; on-device inference | One codebase for every screen size; the CV stack is Python-only and needs a GPU, so it stays on a laptop or Colab | M1 |
| D2 | 2026-10-29 | Pose via RTMDet + RTMPose through rtmlib (Apache-2.0) | Ultralytics YOLO-pose (AGPL-3.0); MMPose directly; torchvision Keypoint R-CNN | AGPL would force the whole project's license; rtmlib runs on onnxruntime without the MMCV install pain. Keypoint R-CNN is the fallback (see D6) | M5 |
| D3 | 2026-10-29 | *Superseded for live sessions by D16; still used for jobs.* The app polls `GET /jobs/{id}` (1 s while running, 3 s while queued, back-off on errors) | WebSockets; Server-Sent Events | Jobs take minutes, so 1 s latency is fine; polling survives Colab tunnels and flaky phone Wi-Fi with no reconnect logic | M1 |
| D4 | 2026-10-29 | *Amended by D30 for the stroke weights.* Weights on the Hugging Face Hub, datasets and clips on a shared Google Drive folder; nothing large in git | Git LFS; GitHub Releases | Free, works from Colab with one call, and keeps the repo small; `scripts/download_weights.py` verifies SHA-256 checksums | M1 |
| D5 | 2026-11-02 | *Amended by D19 (v1.1).* Clip record v1.0 frozen (`schema.py` is the source of truth; snapshot in `backend/tests/fixtures/clip_record.schema.json`). The `schema-v1.0` tag waits for the T1.1 review | Keep the format open until Phase 3 | Six people build against it in parallel; any change after the freeze needs the lead's approval and a version bump | M1 + all |
| D6 | *pending T1.5* | Pose backend: rtmlib `balanced` vs Keypoint R-CNN | — | Filled in after the pose spike on the two test rallies (speed, missed players, keypoint jitter) | M5 |
| D7 | 2026-10-30 | Per-stage cache keyed by a SHA-1 of the stage config, video size and schema version | Re-run every stage on every request | Lets re-render (T5.12) and score corrections reuse perception results instead of re-running TrackNetV3 and pose | M1 |
| D8 | 2026-10-30 | Fake pipeline (`SHUTTLESENSE_FAKE_PIPELINE=1`, `run --fake`) returns the golden record scaled to the video | Mocking in the app only | The app team can develop and demo every screen before the models work | M1 |
| D9 | 2026-10-30 | Player assignment uses a greedy nearest-box match instead of SciPy's Hungarian solver | `scipy.optimize.linear_sum_assignment` | With at most a handful of people per frame greedy is exact enough, and it keeps SciPy out of the base install | M5 |
| D10 | 2026-10-30 | Score corrections are also saved to `corrections.json` in the job folder and applied again after every pipeline run | Write corrections into the referee stage cache; forbid re-render after a correction | The stage cache must stay a pure function of the inputs; a re-render (e.g. to add the scoreboard) must not bring back the uncorrected winners | M1 |
| D11 | 2026-10-30 | Stage cache keys include whether the stage is installed, and a stage that skips itself is cached as skipped | Bypass the cache after any miss; hash every stage's output | Installing weights later reruns that stage and everything after it, while a stable skip stays a cache hit, so re-renders stay fast | M1 |
| D12 | 2026-10-30 | ShuttleSet's Chinese type names map to the paper's English names, then to the 6 classes; 未知球種 ("unknown", 1,407 strokes) is excluded like the drives | Translate the CSVs once on download; drop the unknown rows in the download script | The released CSVs only carry Chinese names, so one table in `strokes/labels.py` keeps both readable; excluding at mapping time keeps the counts visible in the dataset report | M4 |
| D13 | 2026-10-30 | The match split is made from the annotation counts (`make_splits.py --from-annotations`) and committed as `configs/splits.json` before any clip is cut | Split after clip extraction | Fixing the test matches first keeps them out of every tuning step; extraction loses only a few strokes per match, so the class balance is the same | M4 |
| D14 | 2026-10-30 | Training features take the hitter as the player whose wrist is closest to the shuttle at the hit, not ShuttleSet's A/B labels mapped to near/far | Map A/B to sides per set | ShuttleSet's A/B do not say which side of the court a player is on in a given set; the wrist rule is what inference does, so training and inference match | M5 |
| D15 | 2026-10-30 | Training saves one checkpoint per seed and copies the best on val macro-F1 to the default path | One checkpoint, overwritten per run | Reporting mean ± std over 3 seeds (T3.9) needs every run, and the app should load the best one | M5 |
| D16 | 2026-10-31 | Live mode streams JPEG frames from the app to `WS /live` and gets JSON events back; uploaded clips keep REST + polling (D3) | WebRTC; Server-Sent Events plus a frame upload endpoint; keep everything on polling | One socket carries both directions with backpressure we control (newest-frame queue, explicit `degraded` events). WebRTC would add a STUN/TURN and codec stack for one LAN client and still need a data channel for events; FastAPI already serves WebSockets through `uvicorn[standard]`, so no new backend dependency | M1 |
| D17 | 2026-10-31 | Live processing and automated line calls move into scope (PRD v1.2); the referee layer is no longer a stretch | Keep them as non-goals / Future work | The reference demo is a live phone feed with calls; the stage code was already modular enough to run on a sliding window. Calls stay *automated calls with a confidence*, never "official": one camera at 30 fps cannot give certified accuracy near lines, and calls inside the uncertainty band need the user's confirmation | M1 + M3 |
| D18 | 2026-10-31 | Coach chat calls the Claude API from the backend with a key set only in backend settings; the prompt is a compact text digest of the clip record and the model must answer only from it, citing `[t=…s]` moments that the server validates | Local LLM on the laptop GPU; call the API from the app; send video frames | The GPU is busy with perception; a key in the app would leak; frames are not needed to answer questions about the record and would cost privacy and tokens. Without a key the chat is disabled and everything else works | M1 |
| D19 | 2026-10-31 | Clip record v1.1: additive fields (`mode`, `line_calls`, `rally_events`, `coaching`, `chat`, `feedback[].value`); `schema.migrate()` upgrades 1.0 records on load | Major bump to 2.0; keep new data in side files | Every new field is optional with a default, which the DATA_FORMAT policy counts as a minor change; migrating on load keeps old jobs readable in History, and the app accepts any 1.x | M1 |
| D20 | 2026-10-31 | Offline and live share the same stage functions: each stage exposes a pure core over arrays that the batch `run()` and the streaming `stream/` session both call; live uses trailing windows and commits an event once the stage's look-ahead has passed | A separate real-time pipeline | Two copies would drift; a parity test runs a clip through both paths and compares hits, rallies and line calls | M1 + M2 |
| D21 | 2026-11-03 | Match play (games, best of 3, server, service court, interval, change of ends) is a pure function of the rally winners plus the user's `best_of` and `first_server`; a point the system missed is an *award*, a kind of score correction placed before the rally that came next | Detect the server from pose; a separate "manual rallies" file; store the match state per frame | One camera cannot reliably tell who served, but the Laws make the server and service court follow from the score once the first server is known. Deriving everything from the winners means every correction, override, award or undo re-derives the whole match, and awards in `corrections.json` survive re-renders like corrections (D10). Undo covers score changes only: a line-call override is changed by overriding again | M1 + M3 |
| D22 | 2026-11-12 | Doubles moves into scope (Phase 9) and its code lands before the freeze. `PlayerSide` (`near`/`far`) stays the team side for scoring, rallies and line calls; individuals get optional slots `near_2`/`far_2` next to `near`/`far` (= `near_1`/`far_1`), hits get an optional `hitter` slot, and the score stores the first receiver and the current server and receiver slots. Clip record 1.2 is additive and leaves new fields out of the JSON when they are empty | Players as per-side lists (`near: [p, p]`); wait for `v1.0.0`; a separate doubles record | Lists break every singles reader in the backend and the app for no singles gain. Leaving empty fields out keeps singles records, exports and live frames byte-for-byte the same, so the release path does not move. Slots belong to a person, not a court half, because partners swap sides in a rally | M1 |
| D23 | 2026-11-14 | Doubles service in later games: the user names each later game's first server and receiver (`score.game_service`, clip record 1.3; `POST /jobs/{id}/score/service`, live `service` message). They are kept on the job like the start score, so re-renders apply them again; an entry whose server is not on the side that won the previous game is ignored rather than refused | Keep the order for game 1 only; guess the server from pose; store the slots in `corrections.json` | The Laws let the game winners choose, so one camera cannot know it; asking once per game keeps `server_id` and the service check working for the whole match. Ignoring a stale entry (a correction changed who won the game) is safer than failing a re-render | M1 + M3 |
| D24 | 2026-11-04 | Saved live jobs re-render the saved analysis on the recording instead of running perception again | Re-analyse the recording offline | A re-run would change line calls and hits under the user's overrides, score changes and coaching notes; the live analysis is what the referee saw and decided on | M1 |
| D25 | 2026-11-05 | Live frames are placed in frame slots by their capture time; empty slots repeat the last image in playback and add no observations, and long gaps are shortened to the resume window | Use the announced fps; drop the slots | Phones deliver stills unevenly, so times, speeds and the saved video only stay in step with the events when each image sits at its capture time; unobserved slots must not count as evidence (hits, rally ends) | M1 + M2 |
| D26 | 2026-11-13 | One-game matches change ends at 11 like a deciding game (BWF Laws 8.1.3 and the other-scoring-systems appendix) | Change ends only in the third game | The Laws treat a one-game match's only game as the deciding game | M3 |
| D27 | 2026-11-13 | App design tokens: spacing, radius, type scale and `StatusColors` (in, out, uncertain, danger) with 4.5:1 contrast in light and dark, used by every screen | Per-screen colours | Line-call colours were hard-coded and failed contrast in dark mode; one set of tokens keeps courtside views readable at arm's length (PRD "Design principles") | M6 |
| D28 | 2026-11-14 | The stroke classifier is a choice between three algorithms, 1D CNN, LSTM and Random Forest, set per job (`stroke_model`) and stored in the record. All three read the same feature window and give the same six classes | Keep only the CNN; adopt the released BST transformer; ensemble the three | The team wants to compare a convolutional, a recurrent and a classical model on the same input. BST is the only pre-trained model that fits our data, but it is none of the three and needs bones, both players and court positions that the pipeline does not build; it stays as future work. No pre-trained LSTM or Random Forest for COCO keypoints exists (survey in [Phase 11](phases/phase-11-stroke-models.md)) | M1 + M5 |
| D29 | 2026-11-14 | The three models are trained on the pre-extracted ShuttleSet features published with BST (RTMPose COCO-17 joints, TrackNetV3 shuttle, 30 frames per stroke, split by match), mapped to our six classes with the D12 table. Poses are divided by the box diagonal as in those files; the checkpoint stores `pose_norm` and the window length and inference follows them | Wait for our own clips and features (T3.1–T3.5); Hugging Face models on RGB or MediaPipe input | Nothing had been extracted or trained by the Phase 3 gate and the team has no time left. The BST files use the same pose and shuttle models as our pipeline, need no match videos, and train on a CPU in minutes. The reported numbers use BST's split, not `configs/splits.json` (D13), so T3.9 on our own clips stays open | M5 |
| D30 | 2026-11-14 | *Amends D4.* The three stroke weight files are committed under `backend/weights/strokes/`, with SHA-256 values in `download_weights.py`. The Random Forest is saved as plain NumPy arrays (`.npz`, read with `allow_pickle=False`) and walked with NumPy at inference | Hugging Face Hub (D4); Git LFS; a joblib or pickle file of the scikit-learn model | The Hub repo does not exist yet (T0.9) and the files are small. A pickled model can run code when loaded and breaks when scikit-learn changes version; arrays do neither. TrackNetV3 and other large weights stay on the Hub | M1 |
| D31 | 2026-11-14 | scikit-learn (BSD-3) trains the Random Forest and is a training and test dependency only (`requirements/ml.txt`, `dev.txt`); the server needs no new package to run it | Write the forest training in NumPy; make scikit-learn a server dependency | Hand-written training is not worth the risk, but prediction is a short loop over the tree arrays. The Random Forest therefore also runs on a server without PyTorch | M1 |
| D32 | 2026-11-14 | Score corrections, awards and line-call overrides form one decision log ordered by time. Undo takes back the newest of them, and an override given after a winner correction on the same rally replaces it. Overrides are appended (the newest per rally applies), so undoing one restores the earlier call. A decision after the deciding rally that would change nothing is refused (`match_over`, `409`) | Keep two separate lists with corrections always winning; a single undo per list | A referee who taps award, then overrides a call by mistake, expects Undo to take back the override, not the award. With corrections always winning, an override made later silently changed nothing | M1 + M3 |
| D33 | 2026-11-14 | Courtside referee additions in clip record 1.5: a session can join a match under way (`start_games`, games each side already won); a decision can carry a reason (`let`, `fault`, `service_fault`, `misconduct`); a retirement or walkover is a `concede` correction that ends the match; `interval` also covers the 120 s interval between games, with `interval_s` | Points-only start score; free-text decision notes; end a retired match by awarding points | A referee who arrives for game 2 or 3 got the wrong game number, change of ends and match end. Fixed reasons keep exports and the coach digest readable; free text would need moderation and translation. Awarding 21 points to end a retired match corrupts the stats | M1 + M3 |
| D34 | 2026-11-15 | Courtside depth in clip record 1.6: a user-owned decision log, an interval clock and one practice goal per player filter. Scoring stays in the existing referee engine; Undo logs an event and marks its target undone, and timers never score. Live command receipts are scoped by session, client and decision ID and kept across reconnects; reusing an ID for a different command is rejected. Goals survive rebuilt notes and re-rendering; completion is self-reported, with no inferred improvement. Pose serve cues are not fault calls. The expanded scope supersedes the original freeze date but does not waive release evidence | Multi-device roles and longitudinal player profiles (both deferred); a second scoring format | Single-device capture and the existing scoring format remain, so the additions cannot change a score. What the app did not measure, it does not claim | M1 |
| D35 | 2026-11-15 | *Amends D29.* The BST import resamples training clips shorter than the window (24 or 25 frames: one second at 25 fps, matches 1 to 20) to 30 frames with the hit at the centre, instead of zero-padding them at the end. Checkpoints store `window_fps`, and inference samples a clip at another frame rate over the same time span. The three models were retrained; settings were chosen on the validation split with seeds that are not reported, and the test split was evaluated a second time | Centre-padding (kept as `--short-clips centre`; within seed noise of resampling on validation); leaving the import and widening the shift augmentation | End-padding put the hit three frames early with dead frames after it in 61% of the training windows and in almost none of the validation, test or inference windows. Resampling also puts every training window on one time base, which padding does not. Test macro accuracy rose for all three models ([results](results/strokes.md)); since the test split had been seen once, the gain is an estimate | M1 |
| D36 | 2026-11-15 | *Amends D21 and D22.* `near` and `far` always mean the ends of the court at that moment, for rally winners, referee taps and every score field. When the players change ends the score moves with them: points, games won, finished games, server and doubles slots swap ends, and `score.ends_swapped` records it (clip record 1.7). `auto_change_ends` (on by default for new uploads and live sessions, off for stored jobs) does this by the rules; an `ends` decision does it by hand, for a change made early or late, or to cancel an automatic one the players did not make. A line-call override on a rally after the deciding point is refused like any other decision there | Key the score by the team that started at each end and turn it in every display; make a Near / Far tap mean the starting team; a manual-only switch | Everything else is already by end: the camera view, automatic winners, taps, line calls, hits and an older app. Turning the score at the one place it is computed keeps them all right without a second naming. The owner chose taps by the end on screen, scores that follow the players, and automatic changes on by default. Per-player statistics and doubles identities across a change are not solved by this (DATA_FORMAT known limits) | M1 |
